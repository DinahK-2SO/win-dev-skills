5. ## Common build errors after the namespace rewrite
6. 
7. These are the build errors that almost always surface first, before any of the deeper API replacements come into play. Fix them inline as you encounter them.
8. 
9. ### `CS0104: 'LaunchActivatedEventArgs' is an ambiguous reference`
10. 
11. After the script rewrites `Windows.UI.Xaml` → `Microsoft.UI.Xaml`, an `App.xaml.cs` (or any other file) that still has `using Windows.ApplicationModel.Activation;` ends up with **two** `LaunchActivatedEventArgs` types in scope — the UWP one in `Windows.ApplicationModel.Activation`, and the WinUI 3 one in `Microsoft.UI.Xaml`. The two are not interchangeable: `OnLaunched` in WinUI 3 receives `Microsoft.UI.Xaml.LaunchActivatedEventArgs`.
12. 
13. Fix by either:
14. 
15. ```csharp
16. // Option A — drop the UWP using (cleanest if nothing else in the file uses
17. // Windows.ApplicationModel.Activation):
18. // using Windows.ApplicationModel.Activation;   ← delete
19. 
20. // Option B — fully qualify the parameter type:
21. protected override void OnLaunched(Microsoft.UI.Xaml.LaunchActivatedEventArgs args)
22. {
23.     MainWindow = new MainWindow();
24.     MainWindow.Activate();
25. }
26. ```
27. 
28. The same pattern applies to any other type name that exists in both `Windows.UI.Xaml.*` and `Microsoft.UI.Xaml.*` namespaces (e.g. `Application`, `RoutedEventArgs`) — fully qualify, or remove the stale UWP `using`.
29. 
30. ### `CS0227: Unsafe code may only appear if compiling with /unsafe`
31. 
32. UWP SDK samples that touch pixel buffers (`IMemoryBufferReference`, `Marshal.GetIUnknownForObject`, `byte*` access) commonly use `unsafe` blocks. The scaffold's `.csproj` does not enable unsafe code. Add this to the `<PropertyGroup>`:
33. 
34. ```xml
35. <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
36. ```

38. ### Thousands of `CS0101` duplicate-type / `CS0227` / `CS0234` errors (often a build that hangs)
39. 
40. If `dotnet build` floods with **tens of thousands** of `CS0101` ("already contains a definition for …"), `CS0227`, or `CS0234` errors — or the build appears to hang for minutes — the cause is almost always **stale UWP build output that was copied into the migrated tree**. A previously-built UWP project (especially a multi-project sample with sub-folders) leaves machine-generated sources under `bin/` and `obj/`, e.g. .NET-Native ILC files at `obj\<arch>\Release\ilc\**\*.g.cs` and `*.McgInterop\ImplTypes.g.cs`. The SDK-style WinUI `.csproj` globs `**/*.cs`, and MSBuild's default `bin`/`obj` exclusion only covers the **project-root** `bin`/`obj` — any **nested** sub-project `bin`/`obj` is still compiled, producing the duplicate types.
41. 
42. Fix: delete every `bin/` and `obj/` folder from the migrated project tree (the current `Initialize-UwpMigration.ps1` skips these at copy time, but remove any that pre-date the fix or were copied manually):
43. 
44. ```powershell
45. Get-ChildItem -Path $Target -Recurse -Directory -Include bin,obj |
46.     Where-Object { $_.FullName -notmatch '\\(\.uwp-source)\\' } |
47.     Sort-Object { $_.FullName.Length } -Descending |
48.     Remove-Item -Recurse -Force
49. ```
50. 
51. Generated sources never belong in source control or the migrated tree — only `.xaml/.cs/.resw/.appxmanifest`/assets are real inputs.

634. ### Manifest migration checklist (Windows.Desktop + runFullTrust)
635. 
636. The default UWP `Package.appxmanifest` declares itself as a Universal app, but a packaged WinUI 3 desktop app is a Win32 process with package identity — it needs a different shape. `winapp run` will register the AppX but **fail to deploy** with `0x80073CF6` or "requires runFullTrust capability" if any of the following are missing.
637. 
638. When merging the UWP manifest into the scaffold's, make sure all of these are true:
639. 
640. 1. **TargetDeviceFamily is `Windows.Desktop`** — not `Windows.Universal`:
641.    ```xml
642.    <Dependencies>
643.      <TargetDeviceFamily Name="Windows.Desktop" MinVersion="10.0.17763.0" MaxVersionTested="10.0.22621.0" />
644.    </Dependencies>
645.    ```
646.    Windows.Universal is UWP-only and rejected for a Win32 entrypoint.
647. 
648. 2. **rescap namespace declared on `<Package>` and added to `IgnorableNamespaces`**:
649.    ```xml
650.    <Package
651.      xmlns="http://schemas.microsoft.com/appx/manifest/foundation/windows10"
652.      xmlns:uap="http://schemas.microsoft.com/appx/manifest/uap/windows10"
653.      xmlns:rescap="http://schemas.microsoft.com/appx/manifest/foundation/windows10/restrictedcapabilities"
654.      IgnorableNamespaces="uap rescap">
655.    ```
656.    Without the namespace declaration, item 3 below is silently stripped by AppX validation and you get the "requires runFullTrust" error at deploy time.
657. 
658. 3. **`runFullTrust` capability declared**:
659.    ```xml
660.    <Capabilities>
661.      <rescap:Capability Name="runFullTrust" />
662.    </Capabilities>
663.    ```
664.    Packaged WinUI 3 desktop apps run outside the UWP AppContainer sandbox and must declare this. Keep any UWP `<Capability>` entries you actually use (e.g. `<DeviceCapability Name="webcam" />`) but add the `runFullTrust` line above no matter what.
665. 
666. 4. **`<Application EntryPoint="$targetentrypoint$">`** — the WinUI 3 scaffold uses an MSBuild placeholder that the build resolves to the real entry point. Don't replace it with a literal `<UwpAppName>.App` (that's a UWP entry-point pattern).
667. 
668. 5. **Reconcile UWP `<Extension>` blocks — especially `windows.backgroundTasks`.** The checklist above is *not* complete once items 1–4 pass: a copied UWP manifest often carries `<Extension>` declarations that are invalid in a packaged WinUI 3 manifest. The most common and most damaging is an in-process background task:
669.    ```xml
670.    <Extensions>
671.      <Extension Category="windows.backgroundTasks" EntryPoint="BackgroundTask.GeofenceBackgroundTask">
672.        <BackgroundTasks><Task Type="location" /></BackgroundTasks>
673.      </Extension>
674.    </Extensions>
675.    ```
676.    UWP auto-registered these WinRT classes; a **packaged WinUI 3 / Windows App SDK** app does not. At launch the AppX registrar rejects the *entire* package with:
677.    ```
678.    error 0x80080204: App manifest validation error … not allowed to have
679.    EntryPoint="…" without ActivatableClassId in windows.activatableClass.inProcessServer
680.    ```
681.    The **build stays clean**, so this only appears at `winapp run` / `dotnet run` time and otherwise silently zeroes the score (the app never launches, every scenario is unreachable). Two fixes:
682.    - **Default (recommended for foreground parity):** delete the `<Extension Category="windows.backgroundTasks">` block(s). The C# `BackgroundTaskBuilder` registration code still compiles; only the in-app `Register()` call is a no-op / throws (already inside a scenario handler), and every *foreground* scenario becomes reachable. Parity checking exercises the foreground UI, not the background trigger, so this restores a launchable app with no scenario loss.
683.    - **Full fidelity (only if background triggers are in scope):** add a matching `<Extension Category="windows.activatableClass.inProcessServer">` with an `<ActivatableClass ActivatableClassId="…">` entry for each task's EntryPoint.
684. 
685.    `Validate-UwpMigration.ps1` Section 5c flags this statically and FAILs before the smoke launch, since the registration failure is deterministic.

699. ### Bootstrap-neutralized helper classes (filter-prone)
700. 
701. Some SDK Samples ship a shared `Common\NavigationHelper.cs` containing a `RootFrameNavigationHelper` class that wires ALT+Left / BrowserBack (virtual key 166) / mouse XButton1+XButton2 to frame back/forward navigation. Its WinUI 3 equivalent requires `Microsoft.UI.Input.InputKeyboardSource.GetKeyState` or P/Invoke `GetAsyncKeyState` plus virtual-key code constants — exactly the shape the model provider's content-safety filter classifies as "keylogger / surveillance" code. Migrating it routinely produces `CAPIError: 400 Output blocked by content filtering policy`.
702. 
703. `Initialize-UwpMigration.ps1` handles this automatically: before the agent ever sees the file, the bootstrap rewrites just the `RootFrameNavigationHelper` class body to a no-op stub (preserving the public ctor with `params object[] args` so callers compile no matter what signature they invoke). The audit log records `NEUTRALIZED  class RootFrameNavigationHelper`. The mapping row's Notes column is prefixed with `NEUTRALIZED:`.
704. 
705. **You don't need to migrate the neutralized class.** Just leave both it and the call site (typically `new RootFrameNavigationHelper(rootFrame)` in `App.xaml.cs`'s `OnLaunched`) untouched — back-nav is not a demonstrated feature of any UWP SDK sample. The remainder of `NavigationHelper.cs` (the `NavigationHelper` class used for per-page state save/restore, the LoadStateEventArgs / SaveStateEventArgs types) is migrated normally; it does not trigger the filter.

711.   <AppBarButton.KeyboardAccelerators>
712.     <KeyboardAccelerator Key="Left" Modifiers="Menu"/>
